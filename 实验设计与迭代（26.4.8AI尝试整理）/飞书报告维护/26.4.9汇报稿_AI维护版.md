## 1. 先讲当前主线架构

### 用图

先放：

- `01_当前19.40主线架构.png`

### 建议时长

`1.5 ~ 2` 分钟

### 建议讲法

我先讲现在这条主线的整体结构。上游还是训练端，一道题一道题去做。每道题做完以后先交给 critic 判断，失败了再由 actor 去调整这道题对应的 skill。这里和最早不一样的一点是，现在为了加速和稳定，我不再一边训练一边在全局 skill 池里做创建、修改、合并，而是改成每道题独立维护一条 task-local skill。这样训练可以并行跑，成功的题最后留下对应 skill。

训练结束以后，会得到一批 task-local skills。因为这些 skill 都是独立的，还不能直接给下游消费，所以中间要先做聚类，再按 cluster 聚合成少量 aggregated skills。现在主线上先固定成 `6` 类。聚合出来以后，下游会先经过 router，router 根据 `name + description` 把题路由到某一个 skill。接下来 executor 消费这个 skill，skill 主要提供两样东西：第一是工具包络，也就是 `allowed-tools`；第二是高层执行 guidance，也就是这类题大致该怎么组织步骤。

### 这一段只讲到这里

不要展开：

- actor / critic 每轮细节
- 创建、合并原语的历史版本
- 经验回放池内部细节

你只要让别人知道现在的流是：

训练单题 skill -> 聚类聚合 -> router 路由 -> executor 消费

就够了。

## 2. 再讲下游形态为什么收口到单 executor

### 用图

切到：

- `02_下游skill消费范式变化.png`

### 建议时长

`1` 分钟

### 建议讲法

接下来讲下游形态。我前面做过一个对比，同样使用上游 skill 的情况下，下游到底是让一个单 executor 直接做，还是拆成 planner、worker、selector 这类协作链路。结果显示，单 executor 更好。

这里最关键的结果是，单 executor 的 `avg_accuracy` 大概是 `0.4476`，拆分式后半段是 `0.3508`；`avg_parameter_accuracy` 这边差距更明显，单 executor 是 `0.2338`，拆分式只有 `0.0010`。这个说明对 Earth-Bench 这种多步工具题，小模型直接在一个 executor 里连续决策更稳。链路拆细以后，它要先规划一条工具链，再逐步执行，这对小模型来说负担更大。

所以当前我先把下游形态收口到单 executor。后面如果换 benchmark，下游未必一定还长这样，但 Earth-Bench 这条线现在先不再摇摆了。

### 这段结束时要落一句

所以从这一点开始，后面所有训练、聚合和测试，都默认服务于单 executor 这个消费形态。

## 3. 再讲成本问题已经先解决一半

### 用图

这段可以继续停留在当前页，或者直接口述，不一定切图。

### 建议时长

`1` 分钟

### 建议讲法

第三点是成本。前一阵训练端如果继续用 `gpt-5.4`，花销很高，所以我做了一轮 `5.2` 的替代实验。结果是，在同一批 `140` 题上，原来高成本线训练是 `107 / 140 = 0.7643`，聚合后测试是 `59 / 140 = 0.4214`；换成 `SSSAI gpt-5.2` 以后，训练是 `94 / 140 = 0.6714`，聚合后测试反而到 `62 / 140 = 0.4429`。

这说明训练侧最贵的模型不是当前主线成立的必要条件。训练分会掉一点，但聚合后测试没有掉，甚至略高。所以现在训练端强模型我先统一换成 `5.2`。这一步主要解决的是成本问题，也把后面继续扩实验的门槛降下来了。

### 这段不要展开

- 不要细讲 pass@k
- 不要细讲 140 题怎么抽
- 不要细讲每轮训练花销

把结论说死就够了：

`5.2` 当前可用，后面训练侧先按它走。

## 4. 接着讲当前最大的工程问题：token 和上下文

### 用图

切到：

- `03_实验主线与关键结论.png`

### 建议时长

`2` 分钟

### 建议讲法

第四点是当前最现实的工程问题，就是 token 和上下文。因为最后评测端要落在本地小模型上，现在用的是 `Qwen3-8B`，输入大概 `32K`。我在跑的过程中发现，很多题的问题集中在上下文中途顶满，不少失败直接来自这里。

这个问题来源有几层。第一层是工具很多，Earth-Bench 原始工具是 `104` 个。第二层是 system prompt 和工具 schema 本身就长。第三层是做题过程中，文件名、参数、tool result 会持续累积，所以真实 request 很快就会到 `30K+`。

这块我做了一个简单实验。原来 `no-skill / all-tools` 的旧基线是 `14 / 60`，加了一个很粗糙的截断机制以后，提升到 `18 / 60`，`Accuracy = 0.3000`。这个说明，原来确实有一部分题是因为上下文超限直接死掉的，做一点截断是有效的。

但更重要的是，带 skill 的方法还是明显更强。当前 `v8` token-budget 结果大概在 `24 ~ 25 / 60`，也就是四十多分。这个说明 skill 的效果不只是“修 token”，它本身就在帮小模型做约束和指导。

### 这一段要收成两个判断

1. token 是当前主线最大的工程瓶颈之一
2. skill 方法的收益依然成立，不能简单理解成只是修了上下文

## 5. 现在讲 skill 在这个 benchmark 上到底起什么作用

### 用图

先放：

- `05_聚合skill字段与消费关系.png`

然后补：

- `04_flat_tree_skill结构对比.png`

### 建议时长

`2 ~ 2.5` 分钟

### 建议讲法

接下来讲我觉得最关键的一点，就是 skill 在这个 benchmark 上到底起什么作用。当前我觉得可以明确压成两个作用。

第一个作用，是约束工具包络。原始 Earth-Bench 工具很多，很重，全部开放给小模型时，它面对的是一个很大的动作空间。现在 skill 里面有 `allowed-tools`，router 路由到某个 skill 以后，executor 只看这一小部分工具，工具空间就收紧了。

第二个作用，是提供高层执行 guidance。skill 不只是告诉小模型“你能用哪些工具”，还会告诉它“这类题通常先 discovery，再 pairing，再统计，最后比较和收尾”。这对小模型是很重要的，因为它最弱的一部分，往往就是把整条工具链先规划得很漂亮。

这里也可以顺手讲字段消费关系。现在顶层字段里，`name + description` 主要给 router 用，`allowed-tools + SKILL.md` 主体主要给 executor 用，metadata 目前主要服务实验复盘。

### 接着讲 flat 和 tree

然后我现在还在比较 `flat` 和 `tree` 两种 skill 组织形式。这里最需要讲清楚的是层次关系。

当前聚合后总共有 `6` 个 skill。每个 skill 都有自己的顶层 `allowed-tools`，这就是硬工具包络。`tree` 的特殊点，是 executor 在进入这个 skill 以后，还会在 skill 内部再选一个 mode。mode 负责更细的 guidance 和工具侧重，但当前 mode 还不是一层新的硬包络。

所以更准确地说：

1. `skill` 顶层 `allowed-tools` 是硬包络
2. `mode` 是内部更细的执行指引

### 如果你想举一个例子

可以用 `task_08_44` 这题。这个例子里：

1. `no-skill` 是直接面对 `104` 个工具
2. `flat` 会先路由到一个较宽的 time-series skill
3. `tree` 会先路由到 ATI 专题 skill，再在 skill 内部选 mode 去细化 guidance

这个例子的意义主要是说明，tree 这条线在结构上更接近“渐进式披露”。当前它还没有在总分上稳定拉开。

### 这一段结尾要落一句

所以当前我对 skill 的理解已经比较明确了：它在 Earth-Bench 上最直接的收益，就是缩小工具空间，以及给小模型补一层高层执行范式。

## 6. 最后讲接下来做什么

### 建议时长

`1` 分钟

### 建议讲法

最后讲一下后续方向。当前我觉得主要有三条。

第一条，是继续做 `flat` 和 `tree` 的错误分析。当前分数已经能说明方法有收益，但还没到一个足够稳的状态，所以要继续拆到底是 skill 写法、executor 行为、closing，还是 answer mapping 在拖分。

第二条，是继续解决 token 问题。当前不管有没有 skill，很多题做到后面都会把 request 顶到二三十 K，所以后面还要继续压 skill 注入体积，也要统一好上下文截断口径。

第三条，是往渐进式披露继续推进。现在 `tree` 已经有点这个意思了。学长下午提到的方向，是以后甚至可以只维护一个总 skill，把多次路由和多层 guidance 全放到 skill 内部去做。我觉得这条线很值得继续尝试，因为它会让外部 skill 个数这个超参变得没那么重要。

### 最后一句收尾

所以当前这条线已经先把基本结构、下游形态、成本口径和 token 问题都梳理清楚了，接下来重点就是继续调分，并把 skill 的组织形式做得更稳。
