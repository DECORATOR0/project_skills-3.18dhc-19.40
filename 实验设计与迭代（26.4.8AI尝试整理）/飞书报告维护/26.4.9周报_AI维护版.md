## 周报正文

### 0. 下游形态：先把消费范式定住

这部分先回答一个总问题：同样使用上游产出的 skill，下游到底该怎么消费。当前对比下来，单 `executor` 的 `ReAct` 形态更稳，因此后续训练侧和测试侧都统一收口到这一种。

| 下游形态 | `avg_accuracy` | `avg_tool_any_order (TAO)` | `avg_tool_in_order (TIO)` | 当前判断 |
| --- | ---: | ---: | ---: | --- |
| `planner / worker / selector` 式拆分协作 | `0.3508` | `0.5927` | `0.4748` | 整体做题效果偏弱，工具链也更容易走偏 |
| 单 `executor` 逐步决策 | `0.4476` | `0.7145` | `0.6555` | 准确率更高，工具轨迹和 gold 的贴合度也更好，后续保留这一形态 |

这里的结论比较直接：对 Earth-Bench 这类多步工具题，小模型更适合在一个 executor 里连续决策。当前不只 `ACC` 更高，`TAO / TIO` 也都更好，说明它在工具选择和执行顺序上都更稳。

### 1. 节约成本：训练端从 `gpt-5.4` 切到 `gpt-5.2`

这部分回答的是成本问题。前期训练端如果继续用 `gpt-5.4`，成本压力过大，所以中间做了 `SSSAI gpt-5.2` 的替代实验。结果表明，这条替代线是可行的，后续训练模型就统一切到 `gpt-5.2`。

| 训练侧口径 | 训练结果 | 聚合后测试结果 | 结论 |
| --- | ---: | ---: | --- |
| 原高成本线 | `107 / 140 = 0.7643` | `59 / 140 = 0.4214` | 训练分更高，但成本高 |
| `SSSAI gpt-5.2` 替代线 | `94 / 140 = 0.6714` | `62 / 140 = 0.4429` | 训练分下降一些，测试侧反而略高，成本更可控 |

这组结果说明，训练侧强模型的价值主要体现在把 task-local skill 训出来，但当前主线并不依赖最贵的模型才能成立。并且在现在的 `v8 formal60` 架构里，训练端也已经达到 `47 / 60 = 0.7833`，说明这条成本替代方案和当前主线是兼容的。

补充一点，学长那边也在做 `Gemma4` 替代尝试。这条线的意义是探索本地可部署模型作为教师模型，等结果出来后再决定是否接入当前主线。

### 2. Token 与上下文：当前工程侧最实在的问题

这部分主要说明，原始 EarthAgent 风格架构在小模型 `32K` 输入条件下，很多题会在中途把上下文顶满。问题来源不只是一张长工具表，还包括题面、协议、多轮工具输入输出、参数列表和历史记忆的持续累积。

#### 2.1 先看上下文压力：全工具开放和 skill 注入后的差异

这里先不急着看分数，先看 executor 在起点到底看到了什么。这里主表统一采用 provider 返回的真实 `input_tokens` 口径，因为这个口径更接近实际运行时的上下文压力。

核心区别很直接：

- 全工具开放时，prompt 里要塞进大量工具说明，再叠加题面、协议和历史轨迹，输入窗很快变紧。
- 加上 skill 后，prompt 里会少掉大部分无关工具说明，新增的是一段 skill guidance。当前看，这个交换是划算的。

| 形态 | executor 起点看到的主要内容 | 工具包络 | 代表性上下文规模 | 当前判断 |
| --- | --- | ---: | ---: | --- |
| 全工具开放的公共起点 | 全量工具说明 + 题面 + 协议 + 历史记忆 | `104` 个工具 | 首轮 `step1 input_tokens` 平均 `29941.5`；全部调用平均 `30197.04` | 首步就已经非常接近 `32K`，后续继续累积会更危险 |
| 当前架构 `no-skill` 示例 `task_08_44` | 同样是全量工具说明，只是加入了 token budget / 截断机制 | `104` 个工具 | `step1 input_tokens = 30100` | 说明即使换到当前架构，只要全工具开放，输入压力依然很重 |
| `flat skill` 示例 `task_08_44` | 该 skill 的 `allowed-tools` 对应工具说明 + flat skill 正文 guidance | `17` 个工具 | `step1 input_tokens = 9449` | skill 本身会占一段上下文，但整体明显轻于全工具开放 |
| `tree skill` 示例 `task_08_44` | 顶层 `allowed-tools` 对应工具说明 + tree skill 正文 + mode guidance | `9` 个工具 | `step1 input_tokens = 6921` | 包络更紧，起点更轻，后续也更容易继续做渐进式披露 |

如果追问“首轮为什么已经接近 `3w`”，当前抓到的直接原因也比较清楚。以 `task_08_44` 这次真实 `step1 request` 为例：

- `system` 消息本体有 `109610 chars`
- `user` 题面与文件预览只有 `2018 chars`
- `system` 里的 `104` 个工具 JSONL 描述块单独就有 `106462 chars`

所以首轮压力主要来自全量工具说明本身，题面只占很小一部分。

这里有两个细节适合在报告里顺手讲清楚：

1. `flat` 和 `tree` 都有顶层 skill 自带的硬工具包络，真正起约束作用的是 `allowed-tools`。
2. `tree` 里的 `mode` 主要是更细的执行 guidance 和工具侧重点，不单独算一层新的硬包络。

补一条口径说明：之前提到的本地静态探针 `step1_prompt_tokens = 9245`，是脚本用本地 tokenizer 对压缩版工具描述做的估算，和 runtime 里真实注入的全量工具说明不是同一口径。它可以用来做相对比较，不适合作为这部分主表里的核心数字。

#### 2.2 再看性能：上下文治理后，各条线分别到了哪里

这里单独列准确率，是为了把“减少上下文爆掉带来的收益”和“skill 本身带来的收益”分开看。

| 方案 | `ACC` | 说明 |
| --- | ---: | --- |
| `Earth-Agent origin` | `12~13 / 60` | 原生单 agent + 全工具轨迹，能跑起来不少题，但最终答对数偏低 |
| 当前架构 `no-skill` + 简单记忆截断 | `18 / 60 = 0.3000` | 先用粗糙截断把一部分“直接爆上下文”的失败救回来 |
| 当前架构 `flat skill` | `24 / 60 = 0.4000` | 在默认 `32768 total / 8192 output` 口径下，已经明显高于 `no-skill` |
| 当前架构 `tree skill` | `25 / 60 = 0.4167` | 继续略高一点，也更符合后续渐进式披露方向 |

这里的简单记忆截断机制，是在某次请求超过上限时，优先裁掉前面非核心请求里的参数层。这是个工程补丁，价值主要在于先把系统从“容易被上下文长度直接打断”拉回到“还能继续做题”的状态。但从结果看，真正把分数继续往上推，还是要靠 skill 对工具空间和执行范式的约束。

#### 2.3 这一段实验带来的两个核心认识

1. 当前 skill 在这个 benchmark 上的第一个价值，是约束工具包络。`104` 个工具全开放时，小模型面对的动作空间太大，上下文压力也更重。
2. 当前 skill 的第二个价值，是提供高层执行范式。小模型不只需要少一点工具，还需要知道这类题通常该怎样分步骤、先做什么、什么时候停。

所以 token 问题当前还没有解决完。即使带 skill，现有 skill 注入体积也依然偏大。`tree` 之所以还有继续做的价值，一个重要原因就是它更容易做细粒度约束；再往后看，更本质的方向还是渐进式披露，让同一条 skill 按需要逐步展开，避免在起点一次性把全部信息塞给 executor。

### 3. Skill 字段约束与下游消费

这部分主要讲 skill 现在是怎么组织的，以及下游分别消费哪些字段。这里的目的，是让 `router` 和 `executor` 的职责边界清楚，避免再把所有信息混在一起。

#### 3.1 当前 skill 字段与消费关系

| 字段 / 结构 | 谁消费 | 当前作用 |
| --- | --- | --- |
| `name + description` | `router` | 负责把题目路由到合适的 skill 或大类 |
| `allowed-tools` | `executor` | 先收紧工具包络，减轻工具选择负担 |
| `SKILL.md` 主体 | `executor` | 提供高层执行骨架、步骤顺序和停止条件 |
| `mode / EXECUTION_GUIDANCE` | `executor` | 只在 `tree` 里继续展开，用来做类内更细的 guidance |
| `metadata` | 记录与复盘 | 用于溯源、实验统计和口径管理 |

这一层的核心目标很简单：`router` 尽量少看字段，只负责找方向；`executor` 负责真正做题时要用到的工具约束和执行 guidance。

#### 3.2 `flat` 和 `tree` 的当前理解

| 形态 | 当前作用 | 现阶段理解 |
| --- | --- | --- |
| `flat skill` | 单层直接注入 | 结构简单，但一口气注入的信息更重 |
| `tree skill` | 先粗路由，再在 skill 内按 `mode` 细分 | 更适合把工具和 guidance 做得更聚焦，本质上是一种渐进式披露 |

当前 `tree` 的意义，主要有两点。一是它能更细地强调工具和步骤，二是它能把多 skill 路由问题拆成两步较轻的决策。对 Earth-Bench 这类模态边界清楚的任务，先在较少的大类里路由，再在类内细分，成本相对低，也更容易继续做精细 guidance。

#### 3.3 一个具体案例：`task_08_44`

如果只用一题来说明下游消费差异，`task_08_44` 很合适。这题是 ATI 月度变化题，三个形态在下游的差异比较清楚。

| 形态 | 初始工具空间 | 下游行为特征 |
| --- | ---: | --- |
| `no-skill / react` 直跑 | `104` 个工具 | 工具空间最大，小模型自己搜索，负担最重 |
| `flat skill` | 顶层 `allowed-tools = 17` | 这题被路由到更宽的 `time-series` skill，硬工具包络已经存在，但题型仍偏泛，注入也更重 |
| `tree skill` | 顶层 `allowed-tools = 9` | 这题被路由到 ATI 专题 skill；顶层 `allowed-tools` 先收紧包络，选中 mode 后再继续强调更贴题的工具顺序和执行重点 |

这里要特别区分两层含义：`allowed-tools` 才是硬工具包络；`tree` 里的 `mode` 更像 mode-specific guidance 和 preferred tools 的强调，不应当再算成一层新的硬包络。这个案例对应的当前理解是：skill 的效果并不只体现在“最后有没有答对”，还体现在下游一开始面对的工具空间有没有被收紧，以及执行范式有没有被拉回正确方向。`tree` 当前还没有在总分上显著拉开，但它已经体现出更细的 guidance 组织潜力。

### 4. 接下来要做的事

1. 继续做 `flat` 和 `tree` 的错误分析，重点看哪些问题来自 skill 本身，哪些问题来自 executor、closing 和 answer mapping。
2. 继续调 `critic` 和 `actor` 的行为控制，提升 retained skill 的修改质量，并把聚合后的 guidance 做得更稳。
3. 继续压缩 skill 注入体积，缓解 token 压力；这块会重点结合渐进式披露去做。
4. 继续往“单一总 skill + 内部多步路由”推进。当前多 skill 和 `mode` 的地位已经越来越接近，后续可以把外部 skill 数量继续收口，把内部层次统一放到一个总 skill 里管理。
5. 在 Earth-Bench 上把这条线调稳后，再迁移到更多任务和 benchmark 上验证泛化。

## 一句话版结论

这周期最重要的收获有四点：下游消费范式已经收口到单 `executor`；训练端可以从 `gpt-5.4` 切到 `gpt-5.2` 控制成本；token / 上下文问题已经确认是当前主要工程瓶颈；skill 在这个 benchmark 上的直接价值，主要体现在缩小工具包络和提供高层执行范式。
