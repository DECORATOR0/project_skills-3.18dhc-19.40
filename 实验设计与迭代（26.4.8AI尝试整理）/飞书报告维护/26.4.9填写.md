### 二、读论文后，我目前比较确定的几点

#### 1. SkillsBench：先确认skill机制有用，以及什么样的skill机制是有用的。

- 这篇回答 skill 本身能不能带来稳定收益。
- 它提示我：curated / high-quality skills 往往有效，但现场自动生成的 self-generated skills 很不稳定，甚至会引入噪声。
- 结论：必须把 skill 质量评估 和 skill 生成/更新机制 分开看，也就是skill质量很重要。

#### 2. SkillCraft：skill如何创建——workflow的角度

- 关注 executable skill，也就是把成功的多步工具链沉淀成可复用 workflow，而不是只保留一段高层提示词。
- 和我现在的实验体验很一致：真正有用的 skill，往往不是一句抽象描述，而是对 工具顺序、输入选择、停止条件 的稳定先验。
- 提示我更关注 skill reuse、workflow abstraction 和 skill verification。

#### 3. AutoSkill：维护可演化的 skill library

- 它把长期交互里的稳定经验抽成可复用 skill，且在测试交互时实时地更新skill库，或许是后续能够追加的一个trick或者说亮点
- memory 更偏“以前发生过什么”，skill 更偏“以后遇到类似任务该怎么做”。

#### 4. EvoSkill：skill 更新里最关键的不是生成，而是验证和选择

- 这篇把 failure analysis -> propose -> build -> validate -> select 的闭环写得比较完整。
- 与前面不同，不仅关注“会不会生成新 skill”，还关注“生成之后怎样验证、怎样筛掉无效更新”。
- 和我们的工作流很像，我们现在的框架可以理解为在它上面的一些改进和深入。

### 三、当前实验

最近在我们的框架的Earth-Bench 上已经做了几轮实验。

#### 1. 先看整条实验主线是怎样收口到当前方案上的

#### 2. 当前最有价值的成对比实验

| 对比组 | 指标 | 结果 | 结论 |
| --- | --- | --- | --- |
| `direct-executor` vs 拆分式后半段 | `avg_accuracy` | `0.4476` vs `0.3508` | benchmark 实分与整体执行效果更支持单 executor 形态 |
| `direct-executor` vs 拆分式后半段 | `avg_efficiency` | `2.1288` vs `0.5936` | 单 executor 在真实做题过程里更顺，额外 handoff 更少 |

| `direct-executor` vs 拆分式后半段 | `avg_tool_exact_match` | `0.4125` vs `0.4357` | 拆分式只在工具链 exact match 上略高，优势比较窄 |

这组对比很重要，因为它决定了后面训练侧和评测侧都应尽量对齐单 executor 消费范式。也正因为这个判断已经比较稳，后续 task-local 训练才会强调“每个 task 维护单条 skill，并尽量和 direct-executor 的消费方式对齐”。

#### 3. `7` 中期训练侧教师模型的成本替代实验

| 对比组 | 训练侧模型 | 训练结果 | 聚合测试结果 | 当前理解 |
| --- | --- | --- | --- | --- |
| 旧 same140 主线 | 原先更强、成本更高的训练口径 | `107 / 140 = 0.7643` | `59 / 140 = 0.4214` | 训练分数更高，但成本压力更大 |
| `7.5 / 7.6` 成本替代线 | `SSSAI gpt-5.2` | `94 / 140 = 0.6714` | `62 / 140 = 0.4429` | 训练分数下降，但测试和聚合结果反而略高 |

这条线的价值主要不在“5.2 一定更强”，而在于它回答了一个很实际的问题：训练侧如果不用 `gpt-5.4`，主线是否还能保住。当前证据说明，至少在当时那批 same `140` 题上，`SSSAI gpt-5.2` 作为成本替代是成立的，训练端会掉一些，但聚合后的测试结果并没有掉，甚至不管走哪种聚合，整体都略高一点。因此这条线本质上解决的是成本问题，而不是单纯追逐更高训练分。

另外，这个判断和当前 `v8` 也能接上。虽然主线已经进入 `8`，但 `v8 formal60` 上当前训练结果也有 `47 / 60 retained`、`Accuracy = 0.7833`，说明在现在这条架构上，用 `gpt-5.2` 继续做训练侧教师模型，效果仍然是可接受的，至少不是当前主线的主要瓶颈。

#### 4. `v8` 这轮把旧线里的几个混杂因素拆开了

| 问题 | 旧线里的表现 | `v8` 当前处理 | 当前收获 |
| --- | --- | --- | --- |
| `family` 先验过强 | 训练和聚合容易先回到旧 family 桶里解释问题 | 不再把旧 `family` 当正式设计边界 | skill 的结构和收益可以单独讨论 |
| `shortlist` 提前给定 | skill 作用和工具空间先验容易混在一起 | 用 `allowed-tools` 承担 executor 硬边界，并统一 skill contract | 不同实验之间的比较口径更干净 |
| `flat/tree` 口径不统一 | 两种形态可能混着不同聚合来源 | 基于同一份 cluster assignment 生成 `flat/tree` | 形态差异可以单独比较 |
| executor 旧 memory 机制 | `flat` 更容易因为 prompt inflation 提前退化 | 切到 token-budget executor 重跑 | 当前已经证实 executor 承载能力会直接影响最终分数判断 |

#### 5. `v8 formal60` 到 token-budget 重跑这一段

| 阶段 | `flat` | `tree` | 观察 |
| --- | ---: | ---: | --- |
| 首轮旧 executor 口径 | `15 / 60` | `18 / 60` | 当时看起来 `tree` 明显更稳 |
| `40960 total / 8192 output` | `25 / 60` | `25 / 60` | 一旦 budget 放开，`flat` 提升非常明显 |
| `32768 total / 8192 output` | `24 / 60` | `25 / 60` | 当前代码默认口径下，两者差距已经很小 |

这条链最重要的结论有两点。第一，`v8` 当前已经能稳定产出 retained skill、完成自动聚类，并在同一聚类结果上生成 `flat/tree` 双评测，主线闭环已经打通。第二，旧口径下看起来像“`tree` 明显更优”的现象，里面包含了很强的 executor memory 因素；切到 token-budget 后，`flat` 的真实能力被释放出来了不少。因此当前更准确的判断是：`tree` 在旧 memory 条件下更稳，`flat` 也有竞争力，后续重点应放在 skill 注入体积、vision 大簇和 closing 逻辑上。

#### 6. 当前对 skill 在这个 benchmark 上作用的两个判断

| 当前对 skill 作用的理解 | 具体解释 | 相关证据 |
| --- | --- | --- |
| 作用一：约束工具包络，缩小小模型面对的动作空间 | Earth-Bench 的工具本身比较重，如果把全部工具和协议直接开放给小模型，prompt 和搜索空间都会明显膨胀。当前 skill 至少能把 executor 需要面对的工具范围先收紧，减轻工具表、协议和多步轨迹一起顶满上下文的问题。 | `no-skill / all-tools` 基线里，`104` 个工具全开放时，静态首轮 `step1_prompt_tokens = 9245`，真实动态调用平均已经到 `30K+`；同时整体结果只有 `14 / 60` |
| 作用二：给小模型提供高层执行范式指导 | skill 不只是“限工具”，还应当告诉小模型这类题通常该怎样组织步骤、优先看什么、什么条件下停。对于 Earth-Bench 这种多步工具题，这类高层 guidance 对小模型尤其重要。 | 当前 `v8` 主线明显高于 `no-skill / all-tools` 和 `Earth-Agent origin`；同时 `direct-executor` 优于拆分式后半段，也说明更稳定的高层执行范式确实重要 |

所以当前更实际的理解不是“skill 是否神奇地学会了所有知识”，而是：在这个 benchmark 上，skill 至少承担了“约束工具空间”和“提供高层做题范式”这两个明确角色。后续如果继续调优，也应主要围绕这两点去判断 skill 是否写得够好、够瘦、够有指导性。

| 路由先把题目归进了更贴切的 task family | `router` 对这题给 `ati-change-monthly-summaries-and-low-ati-anomaly-detection-day-night-thermal-albedo` 打了 `95` 分，而给更泛的 `raster-time-series-aggregation-and-comparison-linear-trend-or-two-period-change` 只打了 `75` 分。 | 这说明当前路由已经不只是“找一个差不多的时间序列 skill”，而是能把题先归到 ATI 专题里，再交给更贴近题意的 guidance。 |
| 高层 guidance 已经开始约束执行顺序 | 这条 `tree skill` 在正文里明确写了 `Discovery is always first`，并要求整体按 `discovery -> helper planning -> ATI generation -> block-local statistics -> final comparison` 往下走，同时把题目进一步约束到 ATI 月度统计这一类。实际执行里，第 `1` 步先 `get_filelist`，第 `2` 步就调用 `plan_ati_by_date.py` 规划 ATI 配对，第 `3` 步在 helper 为空后继续去读 `PAIRING_RULES.md` 做日期归一化核对。 | 这说明 executor 的行为已经被拉回 ATI 专用流程里了，没有在大工具空间里随意发散。即使这题最后失败，失败点也主要落在 ATI 配对和 closing 细节上，而不是任务范式从一开始就走偏。 |

如果把这个案例压成一句话，就是：当前 skill 在这道题上的主要价值，已经能够具体体现为“先把 executor 限制在更小的 ATI 工具包络里，再把它往 ATI 月度汇总这条执行范式上拉”。后续真正需要继续修的，是 pairing helper、归一化规则和 closing 可靠性，而这恰好也是当前 `flat/tree` 错误分析最该继续盯的地方。

#### 7. 目前保留 `tree skill` 这条线的理由

| 维度 | `flat skill` | `tree skill` | 当前理解 |
| --- | --- | --- | --- |
| 结构 | 一条单层 skill，直接给总 guidance | 顶层 skill 下再分 mode / 子类型 | `tree` 的目标不是变复杂，而是把 guidance 组织得更细 |
| 路由方式 | 一次路由到某条 skill | 先粗路由到一个大类，再在类内做一次更细的匹配 | 对 Earth-Bench 这种模态和题型边界比较清楚的任务，先做粗路由的成本其实不高 |
| 工具侧重点 | 更容易把很多工具和规则写在一块 | 可以在 mode 层更有针对性地强调某类工具和步骤 | 这有助于把“题型差异”直接写进 skill 内部结构 |
| 高层 guidance | 更偏统一模板 | 更容易按子任务类型给差异化 guidance | 这正是 `tree` 继续保留的主要意义 |
| 路由风险 | 如果未来开出几十条 skill，单次全局路由准确性会成为问题 | 先在 `6` 个左右的大类里粗路由，再在类内细分，整体路由开销较小 | 这其实也在解决“多 skill 路由”会越来越难的问题 |
| 当前效果 | memory 修复后已经有竞争力 | 目前结果还没有显著拉开 | 说明方向不一定错，但还需要继续调 mode 设计和 guidance 质量 |

如果把这个判断再压缩一点，可以理解成：`tree skill` 本质上就是一种渐进式披露。外层先给较粗的任务结构和工具边界，内层再按 mode 逐步展开更细的 guidance。对于 Earth-Bench 这类题型边界较清楚的任务，这样做可以把路由和 guidance 的展开拆成几步较低成本的决策。

再往前推一步看，当前的多个 aggregated skill，其实和 `tree` 里的多个 mode 在地位上已经越来越接近了。既然核心目标是渐进式披露，那么后面完全可以继续朝“只保留一个总 skill”这条线去收口：外部先只暴露一个 skill 入口，把内部的一次或多次路由、mode 选择、甚至更复杂的执行层次都放到这个 skill 内部去管理。这样一来，外部 skill 数量本身就不再是重点，`k`、候选 skill 数这些超参的负担也会更小。当前这条线还没有正式落地，但它已经是我觉得很值得继续推进的下一个结构方向。

#### 8. 这几天几个专题文档里比较有价值的观察

| 专题 | 关键观察 | 对当前主线的影响 |

| --- | --- |

### 三、接下来要做的点

1. 围绕 `flat` 和 `tree` 做系统错误分析，把失败按题型、执行阶段和 closing 方式拆开看，先确认哪些问题来自 skill 结构本身，哪些问题来自 executor、vision 大簇或最终答案回收。
2. 继续调 `critic` 和 `actor` 的行为控制，重点看 retained skill 的产生条件、更新质量和噪声过滤，争取把训练侧产出的 skill 变得更稳定、更可迁移。
3. 继续调试聚合和注入方式，让 cluster 到 aggregated skill 的表达更可控，减少过肥 skill 对 prompt 和 token 的挤压，争取继续提升当前主线性能。
4. 继续探索“单一总 skill + 内部渐进式披露”的方向。当前 `tree skill` 已经说明，多层 guidance 和多次低成本路由是能被组织进同一条 skill 内部的；后续可以进一步尝试把外部多个 aggregated skill 收口成一个总 skill，把内部的 mode 选择、分层 guidance、甚至更复杂的执行秩序都统一放进去管理，同时减少外部 skill 数量以及相关超参负担。
5. 继续关注训练侧教师模型的成本替代。一条已经验证过的方向是 `SSSAI gpt-5.2`，说明低成本替代是有希望保住主线效果的；另一条正在推进的是学长那边的 `Gemma4` 替代尝试，这对应的是“本地可部署模型作为教师模型”的路线，后续等他那边结果出来，再决定是否进一步接入当前主线。
6. 在 Earth-Bench 上把当前主线继续打磨到更稳之后，再迁移到更多任务和 benchmark 上验证泛化效果。

### 附：如果从聚合端讲当前架构

如果报告时想让别人尽快听懂，我现在更建议这里用“一张简单图 + 一张字段表”一起讲。图不再展开聚合输入那一段，只专注于 aggregated skill 自身的字段约束，以及 `router / executor / trace` 分别消费哪些部分；正文里再用一句话带过“先分 `k` 类再聚合”即可。这样别人更容易抓住重点，也不容易把 `description`、`allowed-tools`、`metadata` 混在一起。

#### 1. 建议按这 3 步讲

1. 聚合端先把 task-local skills 自动聚成 `k` 类，当前固定 `k = 6`；这一句先带过即可。
2. 每个 cluster 生成一份下游可消费的 aggregated skill bundle；同一份 cluster assignment 同时产出 `flat` 和 `tree`。
3. 聚合产物里真正给下游看的字段只有少数几项，而且 router 和 executor 的消费边界是刻意拆开的。

（飞书里可以把 `05_聚合skill字段与消费关系.png` 放在这小节最前。）

#### 2. 当前聚合产物的字段和消费关系

当前聚合产物里，比较值得在报告时点名的字段和消费关系可以压成下面这张表：

| 字段 | 中文含义 | 谁消费 | 当前作用 |
| --- | --- | --- | --- |
| `name` | 对外的 skill 名称 | `router` | 候选 skill 的主标识，需要写成公开、可读、能让小模型抓住题型的名字 |
| `description` | 路由描述 | `router` | 当前主匹配入口，需要显式写出任务锚点、题型形状和核心目标 |
| `allowed-tools` | 工具包络 | `executor` | 硬工具边界，用来把 executor 面对的工具空间先缩小 |
| `SKILL.md` 主体 | 高层执行 guidance | `executor` | 负责执行骨架、步骤顺序、guardrails、helper contract 等主要指导信息 |
| `references/EXECUTION_GUIDANCE.md` | mode 级细 guidance，仅 `tree` 有 | `executor` | `tree` 版在选完 mode 后继续读取，补充更细的 mode 内执行规则 |
| `scripts/`、`references/` 其他资源 | 共享 helper 和参考文件 | `executor` | 只有在 `SKILL.md` 主体明确引用时才会继续调用或读取 |
| `compatibility` | 当前 skill 的版本/形态标记 | 当前主要用于口径管理 | 标记它属于 `aggregated-v2-flat` 还是 `aggregated-v2-tree` |
| `metadata.schema_version / skill_shape / aggregation_model / source_* / generated_at / shared_resource_count` | 结构形态与溯源信息 | 当前主要用于实验记录、统计与复盘 | 这部分当前先不承载额外路由语义，主要服务复盘和比较 |

#### 3. 当前这套字段设计的核心原则

这套设计的核心，是把 `router` 和 `executor` 的职责拆开讲清楚：

- `router` 当前只看 `name + description`，它要的是短、小、稳定的路由表面。
- `executor` 当前才看 `allowed-tools + 完整 SKILL.md + resources`，它要的是可执行 guidance 和更小的工具空间。
- `metadata` 先只承担溯源和实验记录职责，这样实验解释会更干净。

当前明确先不放回聚合产物里的旧字段包括：

- `family_id`
- `domain`
- `benchmark_question_range_prior`
- `route_signals`
- `training_buckets`

这些字段一旦重新混进聚合 skill，很容易把旧系统先验再带回运行时，后面分数就会更难解释。

#### 4. 后续可尝试的优化点

这里还有一个后续可以尝试的优化点。当前这套字段集合是我们先人为固定下来的，优点是 contract 清楚、实验口径也比较干净。学长提到，后面可以进一步放宽：针对不同的下游，让强模型先分析“什么字段最利于当前 consumer 使用”，再自己指定更有利于下游消费的字段组织，然后再做聚合。比如，router 更重的下游，可以让它自动强化 routing surface；executor 更重的下游，可以让它自动决定 mode index、helper contract 和 references 应该怎样组织；分析型下游，则可以保留更丰富的 metadata。当前更稳妥的做法，是把 `name + description + allowed-tools + executable guidance` 继续作为最小稳定核心，其余字段按下游需要逐步扩展。
