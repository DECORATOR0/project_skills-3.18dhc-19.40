## 3. 当前主线目标

当前主线可以压成一句话：

- 用 task-local 训练沉淀 retained skills，再做一次自动聚类，产出共享同一聚类结果的 `flat/tree` 两套 aggregated skill library，并继续提升其在 `formal60` 上的执行质量。

当前主线已经进入下一阶段：

- `v8` 已经能跑通，下一步要把分数继续从 `20+ / 60` 往上抬

## 4. 当前已经冻结的设计约束

这些约束现在应该视为主线默认值，不建议再在旧大文档里来回摇摆。

### 4.1 训练与聚合侧

- 不再保留旧 `family` 语义作为正式设计边界。
- 训练阶段沉淀的是 task-local skill，不再先验塞回旧 family 桶。
- 聚合阶段先做一次自动聚类，再基于同一份聚类结果分别生成 `flat` 与 `tree`。
- 当前聚类数仍固定为 `6`，但它们不再等价于历史 family。

### 4.2 路由与执行侧

- `router` 只看 `name + description`。
- `allowed-tools` 负责 executor 的硬工具边界。
- 其余 guidance 由 `SKILL.md` 主体承担。
- `tree` 只允许两层：
  - 顶层 skill
  - skill 内 mode

### 4.3 skill 形态侧

- `flat` 是单层 aggregated skill。
- `tree` 是带 mode index 的二层 aggregated skill。
- `flat/tree` 的差异只应体现在 skill 内表达结构，不应该再分别做两次聚类。

### 4.4 模型与接口口径

- 聚合强模型仍是 `gpt-5.2`。
- 小模型口径统一收口到 `Qwen3-8B` 的 streaming + thinking。
- executor 当前代码默认 token budget 为：
  - `executor_total_token_budget = 32768`
  - `executor.max_tokens = 8192`
  - 即默认 input budget = `24576`

相关代码位置：

- `nlrl_skills/config.py:45-47`
- `nlrl_skills/agent_loop.py:295-300`

## 6. 当前横向对照怎么看

把目前最有代表性的几条线放在一起，可以得到下面这张判断表：

| 线别 | 结果 | 当前解读 |
| --- | --- | --- |
| `no-skill / all-tools` | `14 / 60` | 纯放开工具不够，skill 仍有显著价值 |
| `v8 flat` 原始首轮 | `15 / 60` | 单层 skill 在旧 memory 口径下受伤很重 |
| `v8 tree` 原始首轮 | `18 / 60` | 旧口径下 `tree` 明显优于 `flat` |
| `v8 flat` token-budget | `24~25 / 60` | memory 修复后提升最大 |
| `v8 tree` token-budget | `25 / 60` | 依然稳，但不再像旧口径那样显著领先 |
| `Earth-Agent origin` | `12~13 / 60` 简单准确率 | 原生架构完成率高，但 final answer closing 很弱 |

从这个对照里，当前最重要的结构性结论有两条：

1. `executor` 的 memory / budget 机制对 `flat` 的影响非常大，不能再把旧 `flat` 低分简单理解成“single-layer design 天生差”。
2. skill library 仍然明显有价值，因为 `no-skill / all-tools` 与 `Earth-Agent origin` 都没有自然超过当前 token-budget 的 `v8` 线。

## 7. 当前最合理的优先级

如果继续做下一轮，建议优先级按下面排。

### 7.1 第一优先级：继续收 executor 注入体积

原因：

- 现在最大的证据说明，即使扩大到更高 token budget，真实题目仍然很容易贴近输入上限。
- skill 过肥仍然是系统级问题。

重点方向：

- 压缩 `system`
- 压缩 `user` 里注入的 skill block
- 能后置到 `references` 的信息不要都塞进主 prompt

### 7.2 第二优先级：修 `vision` 大簇

原因：

- 它在原始 `formal60` 首轮里是最主要的拖分项。
- 即使 memory 修正后，`vision` 仍然不稳。

### 7.3 第三优先级：修 discrete compare / peak-date / answer closing

原因：

- `water/index`、`period compare`、`MC answer mapping` 一类错误在多条线里都反复出现。
- 这类问题往往集中在后半段 decision logic 不稳，工具调用能力本身未必是主因。

### 7.4 第四优先级：把 executor 默认预算口径定死

当前有两个都跑过的口径：

- `40960 total / 8192 output`
- `32768 total / 8192 output`

而代码当前默认是后者。建议后续不要再在旧文档里口头混写，必须明确区分：

- “当前代码默认值”
- “当前最好的一次实跑值”
