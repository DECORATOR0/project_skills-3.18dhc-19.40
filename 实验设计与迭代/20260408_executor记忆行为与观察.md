# `executor` 记忆行为与观察

## 1. 目的

这份文档单独记录 `project_skills-3.18dhc-19.40` 当前测试链路里，`executor` 在多步执行时到底把什么记忆带进下一步，以及我们围绕它已经确认的行为与现象。

后面如果再讨论：

- 为什么 `step2` 开始像“失忆”
- 为什么会反复调用 `get_filelist`
- 为什么 `flat` 比 `tree` 更容易出奇怪的多步问题
- 为什么一个 skill 变长后，executor 行为会明显恶化

就不需要再把这部分混在总实验文档里反复展开。

---

## 2. 先说结论

先加一个补充说明，避免后面混淆：

- 本文第 `2` 到第 `14` 节主体描述的，是当时已提交的 `nlrl_skills` executor 压缩模式。
- 那一版对应 `git` 里可追溯的 `1600 / 600 chars` 历史压缩逻辑，而不是当前工作区后来出现的 token-budget 版。
- 如果后面你看到当前 rerun 的 request 大量精确打到 `24576 tokens`，那已经不是本文主体最初观察到的这一版，而是后面新增的另一种模式。

先把目前已经确认的结论钉死：

- `executor` 的理想多步记忆不是“只看当前题面”，而是一个持续累加的 message 链。
- 这条链最少应包含：
  - `system`
  - 当前 task + 当前激活 skill 的 `user`
  - 前面每一步的 `assistant` 工具调用 JSON
  - 对应每一步的 `tool result`
- 如果不爆上下文，`step N` 的请求里，理论上应该保留直到 `step N-1` 为止的整段历史。
- 当前实现不是按 token 控制，而是本地 wrapper 先按字符数做裁剪。
- 当前裁剪链条不是一刀切，而是：
  - 旧消息先压到 `1600 chars`
  - 如果还不够，再压到 `600 chars`
  - 如果还不够，再直接丢整条旧消息
- `system + user` 这前两条消息优先级最高，几乎总是被保留。
- 一旦 `system + user` 本身已经很肥，后面的历史会被迅速挤掉，`executor` 在 `step2` 以后就会越来越接近“只剩题面和 skill”。
- 这类问题不是单纯“8B 模型太弱”，而是明显带有系统级记忆预算挤压特征。

## 3. 理想情况下，`executor` 每一步应带什么记忆

如果没有上下文预算问题，那么 `executor` 在第 `k` 步发请求时，应当看到下面这条完整链：

1. `system`
2. `user`
3. `assistant(step1)`
4. `user(tool result step1)`
5. `assistant(step2)`
6. `user(tool result step2)`
7. `assistant(step3)`
8. `user(tool result step3)`
9. ...
10. 一直到 `assistant(step{k-1})`
11. `user(tool result step{k-1})`

也就是说：

- 当前 step 的 `system` 人设和工具协议还在
- 当前题面的 task payload 还在
- 当前激活 skill 的全文 guidance 还在
- 前面已经做过的工具调用与返回结果也都还在

这才是多步 agent 正常工作的理想形态。

---

## 4. 当前实现里，`system` 和 `user` 里分别装了什么

### 4.1 `system` 里有什么

`system` 不是 skill 本体。

它主要装的是：

- executor 身份与执行纪律
- JSON 工具调用协议
- 可用工具列表及 schema

因此它更像“执行器底座”，而不是某一道题的具体求解方法。

### 4.2 `user` 里有什么

当前 `user` 才是题目级注入的主体，主要包含：

- task payload
- 激活的 skill 名称
- 完整 `SKILL.md`
- bundled resources 的路径列表
- 若干 execution reminder

因此当前 skill 变长，最直接膨胀的是 `user` 这一段，而不是 `system`。

---

## 5. 当前多步历史是怎么被构造出来的

当前 `executor` 的 message 链大体由下面几部分拼起来：

- `nlrl_skills/agent_loop.py`
  - 初始化 `system + user`
  - 每轮把模型返回的 JSON 作为新的 `assistant` 消息追加进去
  - 每轮把工具执行结果包装成新的 `user` 消息追加进去
- `nlrl_skills/environment.py`
  - 把 `task_json + skill_md + resources_json` 渲染进 executor 的 `user_prompt`
- `prompts/executor_user.md`
  - 定义 `user` 注入模板

所以当前 `executor` 的本质不是“每一步重新独立回答”，而是“带着历史 messages 反复续写”。

---

## 6. 当前裁剪机制到底是什么

这里最重要的是：当前实现先按字符数裁，不是按 token 裁。

核心逻辑在 `nlrl_skills/agent_loop.py`，目前已经确认：

- `_OLDER_MESSAGE_LIMIT = 1600`
- `_MIN_MESSAGE_LIMIT = 600`
- `max_context_chars` 在本轮 `formal60` eval 里是 `48000`

裁剪顺序可概括为：

1. 先找出 tool result 消息。
2. 对较老的历史消息先做第一轮压缩：
   - 很多旧消息被截到 `1600 chars`
   - 但会尽量保住：
     - 最早的前 `2` 个 tool result
     - 最近的后 `3` 个 tool result
3. 然后把所有消息往 `max_context_chars` 里塞：
   - `system + user` 先保留
   - 后面的历史从新到旧尽量塞
   - 塞不下的旧消息会直接整条消失
4. 如果还超预算，再把 `idx >= 2` 的历史进一步压到 `600 chars`
5. 然后再试一次整体塞入预算

因此当前不是只有一个 `[truncated]` 阈值，而是：

- 第一档 `1600`
- 第二档 `600`
- 最后再整条丢消息

---

## 7. `[truncated]` 到底意味着什么

`[truncated]` 只说明：

- 这条消息在进入当前请求前，被本地 wrapper 截断过

它不等于：

- 这段历史已经完全丢失

更不等于：

- 当前请求一定已经不可用了

在很多 case 里，只要关键证据还保存在较完整的 `tool result` 里，旧的 `assistant` JSON 被截成 `1600 chars` 仍然不一定影响执行。

真正危险的是下面两种情况：

- `system + user` 本身就太肥，后面历史被直接挤掉
- 关键 `tool result` 自己也开始被压短或被整条丢掉

## 8. 一个具体例子：tree 的 `task_34_126 step4`

文件：

- `runs/v8_fastline_merged60_20260407_r36/formal60/eval_runs_tree_parallel/formal60_tree_eval_parallel/task_34_126/env/executor/executor_steps/20260407T121923Z_executor_step_4_request.json`

这份 `step4 request` 里实际有 `8` 条消息：

1. `system`
2. `user`
3. `assistant(step1)`
4. `user(tool result step1)`
5. `assistant(step2)`
6. `user(tool result step2)`
7. `assistant(step3)`
8. `user(tool result step3)`

这正好体现了当前 message 链的正常形态：

- `step4` 请求里不会有 `assistant(step4)`，因为那是这次调用即将生成的内容

这份请求的 `messages[].content` 总字符数约为：

- `43722 chars`

按本地 `Qwen3-8B` tokenizer 粗估，大约是：

- `12395 input tokens`

说明 `48k chars` 不等于 `48k tokens`，两者差得很远。

## 9. 一个更关键的现象：flat 会更早退化成只剩 `system + user`

在这轮 `formal60` 里已经看到一个明显现象：

- 某些 `flat` case 到 `step2` 时，请求里基本已经只剩 `system + user`
- 而对应 `tree` case 在同位置还能保住前一步的 `assistant + tool result`

这意味着：

- 问题不只是“模型做错了”
- 更像是 `flat` 版本里，skill 注入更肥，导致后续历史更早被本地字符预算挤掉

一旦退化到这种程度，`executor` 在行为上就会越来越像：

- 每一步重新面对“题面 + skill”
- 但忘掉了自己刚刚已经做过什么

这正是重复 `get_filelist`、重复 blocker、重复第一步工具调用的系统性来源之一。

## 10. 关于 `flat vision skill` 变肥，我们已经确认了什么

当前出问题的 `flat vision skill`：

- `vision-scene-classification-object-detection-and-change-geometry-metrics/SKILL.md`

已经确认的事实有：

- `SKILL.md` 本体约 `13397 chars`
- 约 `247` 行
- frontmatter 里带了 `34` 个 shared resources 路径

这里最容易误解的一点是：

- 这些 `scripts/*.py` 和 `references/*.md` 的内容，不会在 skill 激活时自动全文注入 executor
- 真正注入进去的是：
  - 完整 `SKILL.md`
  - resources 的路径列表

脚本和参考资料正文只有在 executor 显式调用：

- `read_file`
- `run_python_script`

时才会被按需读取。

所以当前上下文压力主要不是“34 个脚本源码全进 prompt 了”，而是：

- skill 本体太长
- helper contract 写得太细
- 再加上一长串 resources 路径列表

这三者一起把 `user` 顶肥了。

---

## 11. 更重要的一点：这些脚本大多并没有真正用上

对这轮 `flat vision` 相关题目的实际轨迹检查后，已经看到：

- 很多题根本没有调用 `run_python_script`
- 也没有调用 `read_file`

也就是说：

- 大量 helper 脚本和 reference 只是在 skill 里形成了“上下文负担”
- 却没有在执行期产生对应收益

这进一步支持了当前判断：

- `flat vision` 的问题不只是 skill 杂
- 还是“把大量 executor 没吃进去的 guidance 先静态塞进 prompt 里”

## 12. 旧本地 `Qwen3-8B` 轨迹给我们的一个参照

按本地 `Qwen3-8B` tokenizer 回放旧 formal run，可以看到：

- 旧的本地 eval 在 `48k chars` 左右时，峰值大约是 `2.2 万 input tokens`
- 当前 tree 示例里，`43722 chars` 大约只有 `1.24 万 input tokens`

这说明：

- 当前 `48k chars` 预算本身非常粗糙
- 同样是 `48k chars`，实际 token 量会随文本形态变化很大

因此当前系统的关键失真点不是“预算一定太小”，而是：

- 用字符数裁切一个本来应按 token 管理的多步上下文

## 13. 当前最稳的观察口径

后面再看任意一个 executor case，可以直接按下面这组口径判断：

### A. 理想保留

特征：

- `system + user` 在
- 前面多轮 `assistant / tool result` 也还在

含义：

- 这是正常多步 agent 形态

### B. 软压缩但还能用

特征：

- 出现 `[truncated]`
- 但关键 `tool result` 还在

含义：

- 历史被压短
- 但未必已经伤到执行主证据

### C. 历史明显丢失

特征：

- 基本只剩 `system + user`
- 或前一步 `assistant / tool result` 已经消失

含义：

- executor 已经接近“多步失忆”
- 更容易重复第一步工具

### D. skill 注入过肥

特征：

- `user` 本体特别长
- skill guidance 很厚
- resources 路径很多

含义：

- 后续历史能留下来的空间被提前吃掉

## 15. 补充校对：为什么它会和当前 rerun 现象不一致

后续再次核对当前工作区后，已经确认：

- 本文主体观察到的不是“更老的 benchmark executor”。

这两件事并不矛盾，因为它们对应的是同一条执行链路在不同时点的两版实现。

## 16. 压缩模式时间线

这里把目前已经确认的几条压缩链按时间顺序单独列清楚。

### 16.1 `agent/skill_eval` 老模式

来源：

- `agent/skill_eval/executor.py`
- `agent/skill_eval/direct_executor.py`
- `agent/skill_eval/config.py`
- `scripts/run_pipeline.py`

核心特征：

- 预算单位是 `chars`
- 默认 `MAX_CONTEXT_CHARS = 16384`
- `tool result` 会先被 `_truncate_text(...)` 压短
- `direct_executor` 里单条 tool feedback 还会把 observation 再压到 `6000 chars`

这是一条更早的 benchmark executor / staged runner 体系，不是当前 `v8_executor_token_budget_*` rerun 在走的主链。

### 16.2 `nlrl_skills` 已提交 `1600 / 600` 模式

来源：

- 关键提交：`696f9c7 align shlab runtime and add 16k context trimming`
- 后续 fastline 提交：`a5d2e39 Add v8 aggregation fastline pipeline`
- 关键文件：`nlrl_skills/agent_loop.py`

核心特征：

- 预算单位仍然是 `chars`
- 先把较老历史压到 `1600 chars`
- 不够再压到 `600 chars`
- 还不够就直接丢整条旧消息
- `system + user` 优先保留
- 会额外尽量保住最早 `2` 个和最近 `3` 个 `tool result`

本文第 `2` 到第 `14` 节主体记录的，就是这条模式。

### 16.3 `nlrl_skills` 当前工作区未提交 token 模式

来源：

- 当前工作区未提交改动：
  - `nlrl_skills/agent_loop.py`
  - `nlrl_skills/config.py`
- 当前 rerun 入口：
  - `scripts/rerun_v8_eval_from_existing_agg.py`
- 运行时调用链：
  - `rerun_v8_eval_from_existing_agg.py`
  - `nlrl_skills/environment.py`
  - `nlrl_skills/agent_loop.py`

核心特征：

- `max_context_chars` 被移除，不再作为 `nlrl_skills` runtime 生效
- 改为：
  - `executor_total_token_budget`
  - `executor_tokenizer_path`
- 每轮调用前，先按 Qwen tokenizer 计算完整 prompt token 数
- 再按 token 预算做消息级 / turn 级裁剪
- 因为采用“尽量塞满上限”的二分搜索截断，所以会出现大量 request 精确等于上限

当前 `v8_executor_token_budget_formal60_20260408_r5_c20` 看到的 `24576` 打满现象，来自这一版。

## 17. 当前 token 模式会怎么截断

下面只讲当前工作区未提交的 `nlrl_skills` token 模式，也就是当前 rerun 真正在走的逻辑。

### 17.1 预算是怎么得到的

当前 `executor` 每轮发请求前，会先取：

- `executor_total_token_budget`
- `executor.max_tokens`

然后计算：

- `max_input_tokens = executor_total_token_budget - executor.max_tokens`

以当前这轮为例：

- `executor_total_token_budget = 32768`
- `executor.max_tokens = 8192`
- 所以理论输入上限是：
  - `24576`

因此现在看到大量 `input_tokens == 24576`，本质上不是偶然碰巧，而是这轮 runtime 的硬上限。

### 17.2 token 是按什么口径算的

不是简单对 `messages[].content` 各自编码求和，而是先按 Qwen chat template 渲染整段消息链：

1. `system`
2. 后续 `user / assistant / user / assistant ...`
3. 最后再补一个 generation prompt

也就是说，真实计数包含：

- role 包装符
- 模板额外 token
- 最后的 assistant 起始提示

因此你在 `request.json` 里直接肉眼估的长度，和最终 usage 里看到的 `input_tokens` 不会完全一样。

### 17.3 截断的总体顺序

当前 `_prepare_messages_for_call(...)` 的逻辑可以概括成：

1. 先检查完整 `messages` 是否已经在 `max_input_tokens` 以内。
2. 如果没超，就原样发送。
3. 如果超了，先无条件保留前两条：
   - `system`
   - 初始 `user`（题面 + 激活 skill）
4. 后续历史不再按单条 message 处理，而是按 turn 处理：
   - 通常是 `assistant(step_k)` + `user(tool result step_k)`
5. 从最新 turn 往最旧 turn 倒着尝试塞入。
6. 只要某个 turn 整体还能放下，就整段保留。
7. 一旦某个 turn 整体放不下，就对这个 turn 做“局部裁剪”。
8. 局部裁剪成功后就停止，所有更老 turn 直接丢弃。

所以当前不是“把所有旧消息都均匀压短”，而是：

- 优先保住 `system + user`
- 再优先保住最近历史
- 压不下时只裁最近那个放不下的 turn
- 更老历史直接不要了

### 17.4 一个 turn 内部先裁谁

当前 turn 内部裁剪有明确偏好：

- 优先裁 `user`
- 再裁 `assistant`

这意味着对于标准 executor 多步链：

- 更容易先被裁掉的是 `Tool result for step k`
- 然后才是上一步的 `assistant(step_k)` JSON

如果是只剩前两条 `system + user` 都已经太长的极端情况，也会优先裁初始 `user`，最后才轮到 `system`。

### 17.5 为什么很多 request 会精确等于 `24576`

因为当前不是粗暴砍一刀，而是做了一个“尽量贴着上限”的搜索：

- 对要裁的那条消息先按 token 编码
- 再用二分搜索找一个最大可保留前缀
- 目标是让整体 prompt 尽量贴着 `max_input_tokens`

因此只要进入“需要裁这个 turn 才能塞下”的分支，最后很容易出现：

- `input_tokens == 24576`

这正是你现在在 run 里看到的大量打满现象。

### 17.6 `[truncated]` 在当前 token 模式里代表什么

在当前 token 模式里，`[truncated]` 的含义是：

- 这条单独消息已经被 token-budget 裁过
- 保留的是一个尽量长的前缀
- 后缀被丢掉了

它不等于：

- 整个 turn 还在
- 更老历史还在
- 当前请求只是“轻微压缩”

因为当前逻辑在裁完这个 turn 之后就会停止继续保留更老 turn，所以一个 request 里虽然只看到一个 `[truncated]`，其后面往往还伴随着：

- 更老若干 step 的整段历史已经完全消失

### 17.7 当前 token 模式和旧 `1600 / 600` 模式最本质的区别

旧 `1600 / 600` 模式更像：

- 先把很多旧消息统一压扁
- 再在字符预算里尽量塞

当前 token 模式更像：

- 完整计算真实 token 预算
- 优先保住最近 turn
- 在第一个放不下的 turn 上做精确局部裁切
- 然后停止，丢掉更老历史

所以新模式的行为会更“硬”一些：

- 不会把所有历史都压成一堆 `1600 / 600`
- 更容易出现“最近几步还比较完整，但更老历史整段消失”
- 也更容易出现 usage 精确贴顶

### 17.8 当前 run 里的一个直接观察

同时也观察到极少数异常样本实际 usage 超过 `24576`，这和“理论截断逻辑”不完全一致，属于另一类问题，后续应单独追查，不应和主截断机制混在一起解释。

## 18. 补充校对：EarthAgent 公开实现对应的记忆机制

这次顺手把 `EarthAgent` 也核了一遍，但要先说明一个前提：

- 当前本地 `/data/xsy` 下没有已克隆的 `earthagent` 项目。
- 当前 GitHub 可查到的 `earth-insights/EarthAgent` 公开仓库，README 明确写的是代码暂缓公开。
- 该 README 直接指向 `earth-insights/GeoPlan-bench`，并说明可以用那个 repo 复现论文结果。

因此现在能实际看到的公开 `EarthAgent` 执行实现，不是一个独立放出的私有 executor，而是：

- `geoplan_bench/agents/EarthAgent.py`
- `geoplan_bench/agents/ReAct.py`

核对后可以确定：

- `EarthAgent` 本身不是一个持续累积单条 `messages` 链的单 executor。
- 它更像一个三层专家选择 / 调度器：
  - 第 3 层先选集成型 expert
  - 第 2 层再选视觉理解 expert
  - 第 1 层再选数据获取 / 预处理 expert
- 真正逐步执行工具的是每个 expert 内部的 `ReActAgent.run(...)`。

而 `ReActAgent` 的记忆机制是：

- 记忆载体不是 role-separated message list，而是一个纯文本 `history` 字符串。
- 每一步往 `history` 里顺序追加：
  - `Thought: ...`
  - `Action: ...`
  - `Observation: ...`
- 下一步的 thought prompt 和 action prompt 都会把整段 `history` 原样放回 prompt。
- 同时它还会从 `history` 里解析出 `previous_tool_calls`，显式提醒模型不要重复调用。

公开代码里没有看到：

- 本地字符预算裁切
- 本地 token budget packer
- `[truncated]`
- “优先保 system + user”
- “优先保最近 turn”

也就是说，公开 `EarthAgent / ReActAgent` 的记忆更接近：

- 每个 expert 自己持有一条完整文本 history
- 不做本地截断
- 靠 `history + previous_tool_calls` 防循环

但它和当前我们这边的单 executor 也不是完全同一件事，因为：

- `EarthAgent` 不是所有专家共用一个全局 history。
- 每个 expert 的 `run(...)` 都是从自己的空 history 开始。
- 层间信息传递主要靠：
  - 子任务 `subtask` 文本
  - 上一层或其他 expert 的结果列表 `results`

所以如果说“当前 1-executor 想和 EarthAgent 对齐”，更准确的说法应是：

- 对齐的是“单 agent 逐步做题、保留前序轨迹、避免重复工具”这类行为风格。
- 不是对齐它的层级架构。
- 也不是对齐任何现成的 `1600 / 600` 或 token-budget 截断机制。

## 19. 目前已经出现过的记忆机制总览

这里把目前已经确认出现过的几类 executor / executor-like 记忆机制统一收口。

### 19.1 `EarthAgent / GeoPlan-bench` 公开 `ReActAgent` 模式

- 载体：单个 expert 内部的纯文本 `history`
- 累积方式：每步追加 `Thought / Action / Observation`
- 裁剪单位：无本地裁剪
- 保留策略：整段 history 原样回灌
- 额外机制：从 history 解析 `previous_tool_calls`，显式防重复调用
- 备注：这是公开 `EarthAgent` 能看到的实际执行形态，但它是“分 expert 的局部 history”，不是单一全局 executor message 链

### 19.2 `nlrl_skills` 最早单 executor 模式

- 对应提交：`88b9430` 根提交，以及后续 `df33a3d / a2d8573` 之前这条链
- 载体：`messages = [system, user, assistant, user, ...]`
- 累积方式：每步把模型输出追加成 `assistant`，把工具结果追加成新的 `user`
- 裁剪单位：无本地裁剪
- 保留策略：完整历史原样发送，限制主要交给服务端上下文窗
- 备注：这是最早真正的 `nlrl` 单 executor 机制，不是 `1600 / 600`

### 19.3 `agent/skill_eval` 拆分式 staged executor 模式

- 载体：不是一条持续 assistant/user 对话链，而是：
  - `prior_steps`
  - `latest_observation`
  - `planned_tool_context`
- 裁剪单位：`chars`
- 裁剪点：
  - `observation` 会先过 `_truncate_text(..., MAX_CONTEXT_CHARS)`
  - 拼给 parameter worker 的 `context` 也会再过一次 `_truncate_text(...)`
- 默认上限：`MAX_CONTEXT_CHARS = 16384`
- 备注：它更像“摘要式上下文”，而不是多轮 message 记忆

### 19.4 `agent/skill_eval/direct_executor` 单 executor 模式

- 载体：持续累积的 `messages`
- 初始形态：`system + user`
- 每步追加：
  - `assistant` 的 JSON 输出
  - `user` 侧的 `Tool result for step k`
- 裁剪单位：`chars`
- 裁剪点：
  - `Tool result` 里的 `observation` 单独压到 `6000 chars`
  - 通用 `_truncate_text(...)` 默认还是 `MAX_CONTEXT_CHARS = 16384`
- 备注：这是单 executor，但不是统一的整段历史 budget packer；更像“对 tool feedback 做字段级止血”

### 19.5 `nlrl_skills` 已提交 `1600 / 600` 模式

- 对应提交：`696f9c7`
- 载体：持续累积的 `messages`
- 裁剪单位：`chars`
- 保留策略：
  - `system + user` 优先保留
  - 较老历史先压到 `1600`
  - 不够再压到 `600`
  - 还不够再整条丢消息
  - 额外尽量保最近 `3` 个 `tool result`
- 备注：这是第一版真正意义上的 `nlrl` 本地多轮记忆压缩

### 19.6 `nlrl_skills` 当前未提交 token-budget 模式

- 对应当前工作区未提交改动
- 载体：持续累积的 `messages`
- 裁剪单位：`tokens`
- 保留策略：
  - 先保 `system + 初始 user`
  - 后续历史按 turn 从新到旧塞
  - 第一个放不下的 turn 做局部 token 截断
  - 更老 turn 直接丢弃
- 额外特征：
  - 用 Qwen chat template 计数
  - 二分搜索贴顶
  - 因而大量 request 精确打到 `24576`

### 19.7 如果只看“单 executor 逐步做题”主线

把和当前问题最相关的那条主线单独抽出来，其实顺序很简单：

1. 最早 `nlrl` 单 executor：完整历史，不做本地裁切
2. `696f9c7` 后的 `nlrl`：`1600 / 600` 字符级压缩
3. 当前工作区 `nlrl`：token-budget turn packer

而 `agent/skill_eval` 和公开 `EarthAgent` 都是旁边的参照系：

- `agent/skill_eval` 说明这个项目里一直还并存着另一条 executor 家族
- `EarthAgent` 说明“单 agent 保留历史”这件事公开 baseline 也在做，但实现形态并不相同

## 20. 为什么会加上 `1600 / 600` 压缩

这个问题我专门顺着提交、配置和后续实验说明追了一遍。

先说目前能直接确认的事实：

- `1600 / 600` 这套逻辑就是在 `696f9c7 align shlab runtime and add 16k context trimming` 这次提交里一起加进去的。
- 同一次提交里，`executor.max_tokens` 默认值从 `32768` 改成了 `8192`。
- 同一次提交里，README 也补了说明：
  - 当前 `qwen3-8b` endpoint 对 `max_tokens > 8192` 会直接拒绝
  - 更长上下文需要靠 prompt-size controls 处理
- 同一次提交里，runtime 新增了：
  - `max_context_chars = 16384`
- 后续实验文档又明确把这条线称为：
  - `v6_ctx16k`
  - “为了止血做的保守工程试验”
  - “不等于真实 16K token 上下文”

再结合周边文档里持续反复出现的现象：

- `Qwen/Qwen3-8B` 在长 executor 轨迹里容易出现 prompt 膨胀
- 还容易伴随 `429 / TPM limit reached`
- 长 skill 注入和长多步轨迹会把 executor 稳定性拖坏

因此现在能给出的高置信判断是：

- `1600 / 600` 不是因为你在“复刻 EarthAgent 公开实现”而加上的。
- 它更像是在 `shlab runtime` 对齐之后，为了适应：
  - `qwen3-8b` 输出上限收紧到 `8192`
  - 长 executor 轨迹更容易失稳
  - 又不想立刻重写成 token 级 budgeter
  这一组现实约束，而临时加上的本地字符级止血方案。

更直接一点说，它的作用像是：

- 先别让长历史把请求继续无上限膨胀
- 先在本地粗暴但可控地削掉旧消息
- 让 run 先能活下来

而不是：

- 精确模拟一个真实 `16K token` 模型窗
- 或者代表“这就是长期正确方案”

### 20.1 目前仍然追不出来的部分

到现在为止，我还没有找到任何一份明确写下来的记录解释：

- 为什么第一档恰好选 `1600`
- 为什么第二档恰好选 `600`

所以这部分目前只能保守记成：

- `1600 / 600` 的“要解决什么问题”已经基本能追清
- 但这两个具体数字更像是当时拍过一次工程经验值，而不是有一份明文设计说明

### 20.2 现在对这件事最稳的总结

如果只保留一句最稳的话，可以记成：

> `1600 / 600` 这套 `nlrl` 记忆压缩，不是最早的单 executor 机制，也不是从公开 `EarthAgent` 代码直接抄来的；它是在 `2026-04-04` 对齐 `shlab runtime`、同时面对 `qwen3-8b` `8192` 输出硬上限和长 executor 轨迹失稳问题时，引入的一次字符级本地止血方案，而两个具体阈值本身目前没有找到更明确的文字出处。

## 21. 新增观察：把输入窗拉到 `32K`，仍然会顶到输入上限

这部分记录的是 `2026-04-08` 新一轮 `v8_executor_input32k_output8k_formal60_20260408_r1_*` 里的直接观察，和前面主体讲的旧 `1600 / 600 chars` 模式不是同一轮实验。

先记结论：

- 把 executor 输入预算抬到 `32768 tokens` 之后，输入上限问题仍然存在。
- 当前 token-budget 模式并没有因为“窗口更大了”就不再截断；它只是把爆点往后推。
- 因此问题不像是单纯 `24576` 太小，更像是：
  - `system + task payload + skill`
  - 再加多步 `assistant / tool result`
  - 在真实题目上本来就很容易把 prompt 顶满。

### 21.1 一个直接样本：`task_08_44 step3`

样本文件：

- `runs/v8_executor_input32k_output8k_formal60_20260408_r1_flat/eval_runs_flat/formal60_flat_eval/task_08_44/env/executor/executor_steps/20260408T041851Z_executor_step_3_request.json`
- `runs/v8_executor_input32k_output8k_formal60_20260408_r1_flat/eval_runs_flat/formal60_flat_eval/task_08_44/env/executor/executor_steps/20260408T041851Z_executor_step_3_response.json`

这份 `response.json` 里可以直接看到：

- `input_tokens = 32768`
- `output_tokens = 8554`

也就是说，这一轮已经不是之前常见的 `24576` 打满，而是把输入窗抬到 `32K` 后，仍然精确贴顶。

同时这份 `request.json` 里已经能看到：

- 一共 `6` 条消息
- 第 `4` 条 `user` 也就是上一步的 `tool result`，已经带了 `[truncated]`

所以这里要特别注意：

- “打满 `32768`” 不等于“历史完全没压缩”
- 实际情况是：一边截，一边仍然把整体 prompt 顶到了新的输入上限

### 21.2 这个样本里，各部分大致占了多少 token

按这轮实际使用的 Qwen tokenizer 口径回看，这个 `step3 request` 的各条消息大致是：

- `msg1 system`: `5424 rendered tokens`
- `msg2 user`: `4022 rendered tokens`
- `msg3 assistant`: `70 rendered tokens`
- `msg4 user(tool result step1)`: `9400 rendered tokens`
- `msg5 assistant(step2)`: `7125 rendered tokens`
- `msg6 user(tool result step2)`: `6724 rendered tokens`

整条 prompt 连同末尾的 assistant generation stub，一起正好贴到：

- `32768 tokens`

其中 `msg2` 这一条本身也不小。按内容拆开，大致可以记成：

- `Task payload`: `670 tokens`
- `Activated skill name`: `19 tokens`
- `Activated SKILL.md` 到 `msg2` 结尾这一整块：`3328 tokens`

再把上面这块继续拆开：

- `SKILL.md` 本体：约 `2495 tokens`
- `SKILL.md` 后面追加进 `msg2` 的 resources / reminder / envelope 部分：约 `828 tokens`
- `Activated SKILL.md:` 这个标题本身：`5 tokens`

所以如果只看 `msg2` 里的 skill 相关部分，可以粗略记成两层口径：

- `skill name + skill block` 合计约 `3347 tokens`
- 其中“纯 `SKILL.md` 本体”约 `2495 tokens`

### 21.3 这说明了什么

这轮观察最关键的不是“当前样本碰巧打满”，而是：

- 就算把输入预算已经拉到 `32K`
- 长 `system`
- 长 `task payload + skill`
- 再叠加大体量 `tool result`

仍然会在真实 `formal60` 题目里很快撞到输入上限。

因此现在更像是：

- 扩窗只能延后问题
- 但不能根治“多步 executor 轨迹天然会膨胀”这件事

换句话说，当前现象已经不太像“只是我们把窗设小了”，而更像：

- 单 executor 长轨迹本身就容易 prompt 爆长
- skill 注入一肥，爆得更快
- 工具返回一长，马上贴顶

### 21.4 为什么会继续去看 `EarthAgent-origin`

正因为把输入窗抬到 `32K` 之后，问题仍然没有自然消失，所以当前形成了一个新的工作假设：

- 这不一定只是我们这版 executor 压缩器写得差
- 也可能是更原生的 `EarthAgent` 条件下，本来就会遇到 prompt / token 膨胀问题

基于这个判断，后续动作不是继续只盯着本地压缩参数调，而是把 `Earth-Agent-origin` 拉到本地做对照。

当前本地已经有：

- `Earth-Agent-origin/`
- `Earth-Agent-origin/scripts/run_qwen3_8b_formal60_parallel.sh`

而且这个脚本直接指向同一份 `formal60` 题集：

- `/data/xsy/project_skills-3.18dhc-19.40/data/task_sets/parallel_skill_training_seed_20260403_formal60/train_all_60.txt`

所以这一轮新增观察可以保守记成：

- 发现把输入窗拉到 `32K` 之后，executor 仍然会遇到输入上限问题
- 因而开始怀疑“长轨迹爆 token”不只是本地压缩实现的副作用
- 为了把“我们自己的 executor 问题”与“EarthAgent / AP 链路本身的长上下文问题”拆开，已经把 `Earth-Agent-origin` 拉到本地，并搭了同一批 `formal60` `60` 题的对照复现入口

这里先记录动机和动作，不提前把“原生 `EarthAgent` 一定也会爆 token”写成已证实结论；那部分应以对照 run 的实际结果为准。

  - `785123`
- 累计 `output_tokens`：
  - `28658`
- 累计 `total_tokens`：
  - `813781`
- 成功题数：
  - `2 / 10`
- 服务端 `503` 题数：
  - `2 / 10`

如果把它再按“单次 LLM 调用平均”来折一下，大致是：

- 平均每次 `input_tokens`：
  - 约 `30197`
- 平均每次 `output_tokens`：
  - 约 `1102`
- 平均每次 `total_tokens`：
  - 约 `31299`

### 22.3 这组对照最值得记住的不是成功率，而是两个长度口径之间的落差

这一轮里最值得单独记住的，不是 `2 / 10` 这个成功率本身，而是下面这组落差：

- 同样是“`104` 工具、`32K input / 8K output`”口径
- `earth-bench-c-1` 的本地静态首轮探针只有：
  - `step1_prompt_tokens = 9245`
- 但这次 `formal60` 抽样直跑里，按 provider usage 看的真实单次调用平均已经到：
  - `input_tokens ≈ 30197`

也就是说：

- 不能把 `earth-bench-c-1` 上那条 `9245` 直接当成“`104` 工具基线下所有题的首轮长度上界”
- 更不能据此反推“既然工具表本身只占这么多，那真实 executor 跑起来应该离 `32K` 还很远”

从这次抽样里至少能保守落两条观察：

- 对某些题来说，就算只跑 `1` 步，provider usage 里的首轮 `input_tokens` 也已经在 `29961 ~ 30135` 这个量级；典型例子是：
  - `q105`
  - `q43`
  - `q125`
  - `q44`
- 对多步题来说，`max_input_single_call` 基本都贴在 `30K+`，典型值是：
  - `30056`
  - `30430`
  - `31158`
  - `31189`
  - `31355`

所以当前更稳妥的结论应改写成：

- `104` 工具表本身并不会在本地 tokenizer 探针里立刻把 `step1` 撑满
- 但真实 provider usage 下，题目 payload、服务端渲染口径、以及多步 tool result/history 叠加以后，executor 的单次 `input_tokens` 仍然会非常快地逼近 `32K`
- 因而当前 memory / packing 问题，并不能简单地归因成“只是工具表太长”

换句话说，这一轮新增观察把问题进一步收紧成了：

- `104` 工具口径是需要保留的，它没有错
- 但真正需要警惕的，不只是“工具表长度”
- 而是“真实 no-skill 轨迹一跑起来以后，provider 侧 usage 口径下的单次请求长度，仍然会很快靠近输入上限”

### 22.4 这 `10` 题里有没有真的触发当前 executor 的 token-budget 截断

这条需要单独记清，因为只看 `input_tokens` 接近 `32K`，很容易误以为“已经按当前 memory 规则截断过了”。

这次逐条回看 `executor_step_*_request.json` 后，可以先下一个很明确的结论：

- 这 `10` 题里，没有观察到一次真正触发当前 executor token-budget 截断。

判断依据有三层：

- 没有任何一条 request / message 内容里出现显式截断标记：
  - `[truncated]`
- 多步题的消息数都是完整单调递增，没有出现“历史 turn 被裁掉”的迹象：
  - `q206` 是 `2 -> 4 -> 6 -> 8 -> 10 -> 12`
  - `q248` 是 `2 -> 4 -> 6 -> 8`
  - `q174` 是 `2 -> 4 -> 6 -> 8`
- 把这些实际 request 再按本地 `Qwen3` tokenizer 重数一遍后，和 provider 返回的 `input_tokens` 是逐条严格相等的。

这轮里最大的单次 request 也只有：

- `q161 step2 = 31355 input_tokens`

其他最接近上限的点包括：

- `q153 step3 = 31189`
- `q174 step4 = 31158`
- `q206 step6 = 30430`

而这轮 executor input budget 是：

- `32768`

所以更准确的说法应该是：

- 这 `10` 题不是“先被当前 memory / packing 规则截断以后，才落在 `30K+`”
- 而是“request 本身自然已经长到 `29.6K ~ 31.4K`，但仍然没有跨过 `32768`，因此 packer 根本还没触发”

也就是说，这轮观察回答的是：

- **当前 `104` 工具 no-skill 基线，即使还没触发显式截断，也已经能把单次请求自然顶到 `30K+`**

而不是：

- **这批样本已经大量依赖当前记忆截断机制，才勉强没爆**

### 22.5 为什么这次 `104` 工具 no-skill `c20` 会出现 `429/503/timeout`，但 `8.16 r5_c20` 基本没有

这条后面又专门回看了一次，需要和 `8.16` 那轮区分开记。

先确认结论：

- `8.16 r5_c20` 确实也是远端 `qwen3-8b`
- endpoint 还是：
  - `http://35.220.164.252:3888/v1`
- 而且 `flat/tree` 两路几乎是同时起跑的
- 但它们最终 summary 里并没有现在这种成批 `429/503/timeout`

`8.16` 文档里已经记过：

- `c60` 时 provider 明确打出成批 `429`
- 所以才回退到 `c20`
- 回退后的 `r5_c20`，`flat` 正式汇总正常产出，`tree` 只剩 `q42` 长尾中断

这次 `104` 工具 no-skill baseline `60` 题汇总里，provider 侧错误则是：

- `9` 个 `503`
- `7` 个 `429`
- `2` 个 `timeout`

继续拆后会发现，这批错误更像 provider admission / capacity 问题，而不是本地执行逻辑坏了：

- `429` 那 `7` 个 task 全部是：
  - `calls = 0`
  - 也就是首发请求还没真正落到 executor step response，就被上游直接拒掉
- `503` 那 `9` 个 task 里，有相当一部分已经成功跑出 `1 ~ 3` 步
  - 更像服务在处理中途抖掉，而不是一开始 prompt 就非法

更关键的区别在于 **首轮请求体量**。

按 step1 的 provider usage 统计：

- `8.16 flat r5_c20`
  - `avg_step1_input = 9762`
- `8.16 tree r5_c20`
  - `avg_step1_input = 8667`
- 这次 `104` 工具 no-skill baseline`
  - `sample10 avg_step1_input = 29941`
  - `rest50 c20 avg_step1_input = 29836`

也就是说：

- `8.16` 虽然也是 `c20`
- 但它的 step1 只有大约 `8.7K ~ 9.8K`
- 这次 no-skill all-104 baseline 的 step1 则已经是 `29.8K ~ 29.9K`

如果只做一个很粗糙但足够说明问题的“首波在飞 input token 体量”比较：

- `8.16 flat + tree` 双路都按 `c20` 同时算
  - 约 `36.9` 万 input tokens
- 这次 no-skill all-104 单路 `c20`
  - 约 `59.7` 万 input tokens

所以更合理的解释是：

- `c20` 不是一个对所有 executor workload 都稳定的绝对值
- 它只是对 `8.16` 那种 **skill 限定工具面 + step1 较小** 的负载还能扛住
- 对这次 **no-skill + 104 全工具直灌 + step1 接近 30K** 的负载，同一个 provider 在 `c20` 下已经越过稳定边界

另外也要顺手记一条：

- 这次 sample10 更早的时间窗里已经出现了 `2` 个 `503`
- 只是还没放大成 `429`
- 后面的 `rest50 c20` 才进一步变成：
  - `7 x 429`
  - `7 x 503`
  - `2 x timeout`

因此这次错误并不是由单一阈值解释完的，更像是：

- 请求本身更重
- 再叠加当时 provider 负载波动

### 22.6 为什么“不加载 skill”这次反而比带 skill 更重

这里最容易产生直觉误判，所以单独落一条。

这次测的 **不是**：

- “无 skill，且只给 executor 一个已经压缩好的最小工具面”

而是：

- “无 skill，但把 `104` 个真实 MCP tools 的原始 schema 全量直灌进 system prompt”

因此 `no-skill` 并不等于“更轻”。

真实 request 文件里能直接看到这个差别。

当前 `104` 工具 no-skill baseline 的典型 step1：

- `system` message 长度：
  - `109610 chars`
- `user` message 长度：
  - `1262 chars`

而 `8.16` skill 版的典型 step1：

- `system` message 长度：
  - `15860 chars`
- `user` message 长度：
  - `14393 chars`（flat 样本）
  - `12620 chars`（tree 样本）

也就是说：

- 带 skill 时，并不是“什么都没注入”
- 但它注入的是：
  - 1 份 skill guidance
  - 1 个被 `allowed-tools` 收紧后的工具边界
- no-skill all-104 时，则是：
  - 没有 skill guidance
  - 但把 `104` 个原始工具的 `name / description / parameters / source` 全塞进 system prompt

所以当前这轮之所以更重，根本原因不是“没 skill”，而是：

- **没有了 skill 对工具面的压缩**
- **转而把完整的 `104` 工具 schema 直接暴露给 executor**

换句话说，这次测到的其实是：

- `无 skill + 全量原始工具表`

而不是：

- `无 skill + 最小化工具面`

### 22.7 为什么之前带 skill 的实验里，触发上限 / 截断的情况反而更多

这条后面也重新核了，结论是：

- 不能只看 step1 谁更短
- 真正决定是否触发截断的，是：
  - 输入窗大小
  - 多步轨迹长度
  - 历史里累计塞回去的 tool result / assistant action / read_file 内容

先看 **输入窗**：

`8.16 r5_c20` 那轮 runtime 是：

- `executor_total_token_budget = 32768`
- `executor.max_tokens = 8192`
- 所以真正可用 input budget 只有：
  - `24576`

而这次 `104` 工具 no-skill baseline 用的是：

- `executor_total_token_budget = 40960`
- `executor.max_tokens = 8192`
- 所以真正可用 input budget 是：
  - `32768`

也就是说，之前 skill 版更容易“打满”，首先就因为它的输入窗本来就比现在小一截。

再看 **平均步长**：

- `8.16 flat`
  - 平均 `7.58` 步 / 题
- `8.16 tree`
  - 平均 `7.45` 步 / 题
- 这次 baseline sample10
  - 平均 `2.6` 步 / 题
- 这次 baseline rest50
  - 平均 `3.56` 步 / 题

所以当前 baseline 虽然 step1 很胖，但很多题其实死得早、停得早，历史没有滚太长。

而 skill 版虽然 step1 较轻，却更容易被 skill guidance 推进到更长的多步执行轨迹里，于是把历史越滚越大。

再看 **截断发生在第几步**：

- `8.16 flat`
  - `25` 次截断 request，落在 `5 ~ 20` 步之间
  - 平均发生在第 `12.6` 步
- `8.16 tree`
  - `42` 次截断 request，落在 `3 ~ 20` 步之间
  - 平均发生在第 `12.62` 步
- 这次 baseline rest50
  - `9` 次截断 request，只涉及 `4` 个 task
  - 平均发生在第 `9.11` 步

这里最关键的观察是：

- 之前 skill 版的大量截断，并不是因为 step1 就已经太长
- 而是因为它在更小的输入窗里，持续把多步历史往后叠

两个典型样本能把这件事说明得很直观。

`skill/tree q44`：

- step1 只有：
  - `6921 input_tokens`
- 但 step2 因为塞进完整 `get_filelist` 结果，直接到：
  - `20042`
- step3 request 就已经出现显式 `[truncated]`
- 后面多次 request / response 都贴着：
  - `24576`

`no-skill baseline q192`：

- step1 一开始就已经很高：
  - `29693`
- 但后面每步只是多叠几个 `MSCN` 分类结果
- 每条 tool result 只是几百字级别
- 因此一直拖到 step13 才开始出现显式 `[truncated]`

所以更准确的说法是：

- 带 skill 的版本，**初始注入更轻**
- 但它的 **输入窗更小**
- 而且更容易跑出 **更长、更复杂的多步轨迹**
- 历史里还会不断回灌：
  - `get_filelist` 长列表
  - `read_file` 文本
  - `run_python_script` 参数与结果
  - 更长的 assistant reasoning / action JSON

因此它比当前这轮 baseline 更容易触发 executor 的记忆截断，并不矛盾。
