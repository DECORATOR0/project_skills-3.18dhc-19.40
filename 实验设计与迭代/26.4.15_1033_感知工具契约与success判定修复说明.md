# 26.4.15 感知工具契约与 success 判定修复说明

## 背景

这次修复针对两类已经确认的共性问题：

- `Perception.py` 和 `benchmark/model_results.csv` 的契约不一致，导致一批感知工具虽然有离线结果，却在 lookup 阶段落空，最后统一回到 `"Failed to call model"`。
- runtime 当前把 success 定义成“没有抛异常”或“`returncode=0`”。这会把一部分语义上已经失败的调用记成成功，形成假性成功。

本次目标是先把共性的基础设施问题收掉，不把这类错误继续留给 executor 临场兜底。

## 修改范围

- [agent/tools/Perception.py](/data/xsy/project_skills-3.18dhc-19.40/agent/tools/Perception.py)
- [nlrl_skills/agent_loop.py](/data/xsy/project_skills-3.18dhc-19.40/nlrl_skills/agent_loop.py)
- [nlrl_skills/tools.py](/data/xsy/project_skills-3.18dhc-19.40/nlrl_skills/tools.py)

## 修改内容

### 1. 修正 `Perception.py` 的 lookup 与结果解包

核心调整：

- 去掉 `get_model_output()` 对 `pandas` 的依赖，改为直接用 `csv.DictReader` 读取 `model_results.csv`。
- 路径归一化同时支持：
  - 绝对路径里的 `"/benchmark/data/"` / `"/benchmark/earth-bench/"`
  - 结果表里的相对路径 `"benchmark/data/"` / `"benchmark/earth-bench/"`
  - `"earth-bench/"`
- 单图模型统一按 `(model, normalized file_path)` 查找。
- `SM3Det` / `RemoteSAM` / `InstructSAM` / `Strip-R-CNN` 增加 `text_prompt` 过滤。
- `SAM2` 增加 `bbox` 过滤。
- `ChangeOS` 改成按 `(pre_image_path, post_image_path)` 的二元键匹配，覆盖结果表里 `(pre, post)` 形式的行。
- `result` 字段统一做 `json.loads / ast.literal_eval` 解析后再返回，修掉原先把 `matches.values[0]` 当成业务结果使用的问题。

这次修完后，原来最典型的几类退化路径都能直接命中离线结果：

- `MSCN`
- `InstructSAM`
- `SM3Det`
- `RemoteSAM`
- `ChangeOS`

### 2. 补 `image_path -> input_image_path` 兼容别名

在 [nlrl_skills/tools.py](/data/xsy/project_skills-3.18dhc-19.40/nlrl_skills/tools.py) 的 `_normalize_eo_arguments()` 里增加了一个轻量兼容层：

- 如果参数里有 `image_path`
- 且没有 `input_image_path`
- 自动补一份 `input_image_path`

这样做的原因很直接：历史 gold 轨迹和部分 prompt 里还在用 `image_path`，工具签名却只收 `input_image_path`。这类错位会把一些题直接打成显式失败。

### 3. 加强 runtime 的 success 判定，但仍保留两状态

在 [nlrl_skills/agent_loop.py](/data/xsy/project_skills-3.18dhc-19.40/nlrl_skills/agent_loop.py) 里加入了 `_extract_semantic_failure()`，现在会把下面这些情况直接记成 `success=False`：

- 返回字符串里包含明显失败信号
  - `Failed to call model`
  - `unknown mode`
  - `traceback`
  - `exception`
  - `not found`
  - `no such file`
  - `does not exist`
  - `permission denied`
  - `missing required positional argument(s)`
- 返回 dict 且带 `error` 字段
- subprocess 返回 dict，`returncode != 0`
- subprocess 虽然 `returncode = 0`，但 `stdout/stderr` 内部解析后已经带出上述失败信号，例如：
  - `{"error": "unknown mode"}`

这次没有把 runtime 状态扩成三态，还是保留：

- `success=True`
- `success=False`

也就是说，原来文档分析里叫 `degraded` 的那部分语义失败，未来在真实执行链路里会直接落到失败分支。

## 没有改动的部分

- 没有修改 actor / critic prompt 本体。
- 没有修改 `scripts/compare_values.py` 的 mode 集合。
- 没有修改逐题复盘生成脚本。

这次先把最核心的工具契约和 runtime 判定收紧，避免把基础设施 bug 继续转嫁给 executor。

## 验证

### 1. 语法检查

执行：

```bash
python3 -m py_compile \
  /data/xsy/project_skills-3.18dhc-19.40/agent/tools/Perception.py \
  /data/xsy/project_skills-3.18dhc-19.40/nlrl_skills/agent_loop.py \
  /data/xsy/project_skills-3.18dhc-19.40/nlrl_skills/tools.py
```

结果：通过。

### 2. 基于 `model_results.csv` 的定点校验

用与新逻辑等价的脚本对结果表做了 sample lookup，命中结果如下：

- `MSCN(question192/A.jpg)` -> `{'predicted_class': 'MediumResidential', ...}`
- `InstructSAM(question205/A.jpg, storage tank)` -> `28`
- `SM3Det(question241/P0615.png, harbor)` -> `[[...], ...]`
- `RemoteSAM(question228/...jpg, northernmost storage tank)` -> `[559, 228, 583, 253]`
- `ChangeOS(question225 time_pre/time_post)` -> `'benchmark/model_out/question225/change_model.png'`

这说明本次最核心的 lookup 路径已经打通。

### 3. success 语义的定点校验

用等价逻辑验证了下面几类输入：

- `'Failed to call model'` -> 记失败
- `{'returncode': 0, 'stdout': '{"error": "unknown mode"}\\n', 'stderr': ''}` -> 记失败
- `{'error': "RemoteSAM() missing ... "}` -> 记失败
- `{'returncode': 0, 'stdout': '42\\n', 'stderr': ''}` -> 保持成功

### 4. 当前 shell 的局限

当前 `/data/xsy` 这边的默认 Python 环境缺少若干运行依赖，例如：

- `httpx`
- `numpy`
- `fastmcp`

所以没有在这个 shell 里把完整 runtime 从头跑起来做端到端回放。当前验证以：

- `py_compile`
- 针对 `model_results.csv` 的 sample lookup
- 针对 success 判定逻辑的定点脚本

为主。

## 预期影响

- 一批原先会假性返回 `"Failed to call model"` 的感知调用，应该会恢复成正常命中。
- 一批原先被 runtime 记成 success 的语义失败，现在会直接记成失败。
- critic 侧看到的 `tool_trajectory.success` 会更接近真实执行情况。
- executor 后续收到的 tool result 反馈会更干净，减少“工具其实坏了但 runtime 说成功”的误导。
